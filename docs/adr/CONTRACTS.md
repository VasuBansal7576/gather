# Public hackathon execution contracts

These are implementation specifications, not descriptions of shipped code. The PRD governs product scope; this document fixes the shared contracts used by ADRs 001–016. Chief owns changes to these contracts. Workers may choose internal helpers, not alter business semantics. Feature execution remains paused until explicitly authorized.

## C01 — Installation, modes and reference business

- Supported release targets: macOS and Linux with Node 26+. Windows support is not claimed. `npx github:VasuBansal7576/gather` is the target entry; test the packed artifact outside a source checkout. npm bootstrap needs network and may use its normal package cache. No claim of offline installation or zero package-manager cache writes.
- Resolve a writable installation root from the invocation directory, never from npm's package cache. All Gather business state, secrets, staged application builds, runtime and repair artifacts belong beneath that root's `.runtime/`. Treat downloaded package code as read-only; stage/build its versioned app under `.runtime/app/<revision>/`, using an isolated npm cache there. Validate the manifest contains all build inputs. Never modify shell startup, global packages or personal OpenClaw configuration.
- `prepared` and `live` use separate roots: `.runtime/prepared/gather.sqlite` and `.runtime/live/gather.sqlite`; live runtime lives at `.runtime/live/openclaw/` and credentials at `.runtime/live/secrets/`; exactly one business in each, one active mode. Reject a second business in an existing mode. Switching modes changes the active store/provider set atomically; never copy fixtures into live state. The prepared business is not a second tenant reachable from live tools.
- Preserve `GATHER_DATABASE_PATH` for explicit developer use. Do not silently relocate existing `data/gather.sqlite`. Detect it, show its location, and require an explicit copy/import action with a consistent backup and integrity check. Preserve the original; never auto-delete or merge multiple businesses.
- The reference fixture extends the existing **Fictional Glasshouse**, timezone `America/New_York`, USD: one exclusive room, capacity 100, 4-hour package at $50 per guest, $1,000 minimum total, no concessions, no extra taxes/fees (explicit fixture policy, not an assumption for live businesses). Additional setup/teardown takes 30 minutes either side. Unknown live costs never imply profitability.
- Six initial inbox messages: three event inquiries (one complete, one missing date, one conflicting date), invoice, newsletter, vendor pitch. Two independently seeded busy calendar blocks; zero prebuilt offers in the product scenario. Seed the reference commercial facts as explicitly fictional owner-confirmed fixture facts, with source documents and provenance; live mode never inherits them. Preserve the old two-proposal fixture as an explicitly named legacy regression fixture, not the product demonstration. Use a fixed test clock and a documented demo clock anchor so dates do not silently expire.
- Add separate empty, non-event-only, partial-import and connection-failed scenarios. A sent-history fixture may contain cited past replies but is not counted as an incoming inquiry. Reset affects only the selected prepared state after confirmation; acquire the mode lock, stop its runner, close SQLite and safely replace its DB/WAL/SHM set. Refuse live, custom path, symlink escape or another running process. Restart verifies the new seed.
- Mode truth: prepared uses deterministic extraction/knowledge/model stand-ins and simulated provider effects, all labelled; it installs no OpenClaw. The opt-in isolated-runtime harness proves native knowledge, model diagnosis and actual restart separately. Live uses real authorized providers and a real supported model. No fixture evidence counts as live proof.

## C02 — Common identity, input and error envelope

- HTTP/tool input is `unknown` until validated. Business and owner identity come from the active server installation, never model arguments or customer text. Retain existing source-key and owner-principal APIs in `src/identity/` and `src/server/`.
- Planned intake envelope: `sourceKey, provider, accountId, channel, externalId, threadId?, observedAt, receivedAt, contentVersion, contentHash, text, attachments[], senderEvidence?, mode`. `senderEvidence` is connector-attested mailbox/authentication status plus provider record locator (not message-claimed authority); absent/ambiguous proof cannot auto-accept an offer. Provider identity comes from the authorized connector; prepared identity comes from the fixture registry. Voice and MCP adapters use this same boundary. An intake item may be eligible before a booking is fully qualified.
- Identity result: `linked(bookingId) | needs_decision(candidateVersion, fingerprint, candidates) | new_inquiry`. Exact verified links deduplicate; names/sender/date similarities are hints only. Ambiguity blocks booking-specific writes until owner resolution. Never infer a merge from a customer-supplied booking ID.
- Shared errors map to existing service error types rather than replacing them: invalid input (400), unauthorized (401/403), missing record (404), stale/conflicting version or authority (409), budget exhausted (429), provider/runtime unavailable (503). Long-running operations return durable intent identity, not premature success. No raw credential/provider-body errors in UI/logs.

## C03 — Source synchronization and honest absence

- Planned source port: `scan(scope, cursor, limit) -> {records, nextCursor, coverage, exhausted}`, `read(sourceKey) -> {version, content, observedAt}`, and incremental deletion/revocation events. `coverage` includes account, folders/query/window, completed pages, observed records, exclusions, last success and `running | partial | complete | failed`. Complete refers only to that declared scope.
- Initial live scope is owner-visible: selected Drive documents, authorized calendar, recent inbox and sent threads. Start with 30 days and pages of 100 records as configurable scheduling defaults, not a universal relevance cutoff. Prioritize active threads; expand history in 30-day windows when requested or required by a linked inquiry. Test representative older/excluded records; display the window and expansion action. Metadata filtering cannot silently classify unseen mail as non-event.
- Commit source versions and cursor progress together in the existing database. Content/parser-version caching, bounded concurrency of two source fetches, and durable idempotency avoid rescanning unchanged records. Interrupted pages resume without skipping records. Bad/expired cursors trigger a bounded rescan with stable-key dedupe, not data deletion.
- Completed zero eligible inquiries: `Scanned N emails. No event inquiries found` plus scope. In-progress zero: `No event inquiries found yet; scanning continues`. Failure: show connection/import failure and last successful coverage. Relevant inquiry but no price: show inquiry and question, not invented facts. Zero facts: `No business information found yet`.
- Deletion/exclusion/disconnect immediately makes dependent knowledge unusable and blocks affected pending actions. Purge cached source bodies and derived searchable content; retain minimal tombstones, provenance references and immutable terms/receipts needed to explain existing commitments. Accepted commercial snapshots are not edited by source deletion. No timed auto-purge of transaction history in this release; explain retention and provide an explicit local reset/export boundary. Reconnection requires revalidation, not automatic unstaling.

## C04 — Native knowledge and commercial authority

- `KnowledgePort` is a Gather interface, **not a claim that OpenClaw exposes RPCs with these names**: `ingestSource(sourceVersion)`, `proposeCandidates(sourceKey)`, `confirm(candidate, owner, expectedVersion)`, `correct(fact, expectedVersion)`, `invalidateSource(sourceKey, version)`, `query(scope, requirements)`, `snapshotForOffer(scope)`, `health()`.
- Results carry typed claims, source/version/observation/effective period, business/customer/booking applicability, confirmation state and freshness. Source content may be unstructured; commercial assertions must be typed. Native auto-capture/dreaming cannot promote source prose into commercial authority. General wiki text is never an approval record.
- All imported commercial claims begin as candidates. Owner confirmation is required before price, capacity, policy or concession facts authorize an offer; allow batch confirmation of an inspected document's parsed claims. Owner-confirmed scoped exception beats the applicable base rule only within its explicit scope. Conflicting current confirmed claims block the affected decision until a versioned owner resolution. Mere recency does not silently win. Historical customer deals stay historical/scoped.
- OpenClaw native recall plus memory-wiki is selected. ADR-008 owns the supported adapter and capability proof; use documented plugin import/compile/search/get/apply surfaces, no private runtime SQLite/transcript scraping. Prepared mode uses the existing SQLite knowledge service as a labelled simulator. Live has one active knowledge authority; do not dual-write a competing policy database. SQLite retains action/approval snapshots and source/index metadata, not a second live general memory.
- Before cutover, export/read existing confirmed facts through their public service, import with provenance, compare the gate cases, then switch the active port only after verification. Preserve the old store read-only for rollback. A failed gate leaves live knowledge visibly unavailable; no automatic fallback that silently re-authorizes stale facts.
- Re-read versions at action time. Updated policy invalidates affected pending proposals/approvals, not accepted commitments. Store the exact terms/evidence versions used by each offer. Unavailable native recall is not an empty result.
- Native gate: changed price, customer-only exception, deleted source, conflicting claims, unconfirmed injected instruction, restart recall and cross-mode/business denial. A supported API failing this gate is an engineering blocker with captured evidence, not permission to add another knowledge vendor.

## C05 — Qualification, pricing and approvals

- Domain result: `eligible | unrelated | needs_review`, with reasons and extracted candidate fields. Missing date/count/type stays eligible when the request is recognizably an event. Pure unrelated instructions cannot trigger booking actions; mixed malicious content cannot change authority. Deterministic code validates scope/permissions after extraction.
- Readiness is per action. Classification needs only the message. Qualification can ask missing date/time/timezone/count/services. Pricing requires confirmed package/currency/terms/capacity, resolvable duration and resource-scoped availability. Sending requires a feasible frozen offer, recipient, exact approval and fresh conditions. Unknown costs permit no profit claim; a configured margin rule with unknown costs blocks.
- Use existing deterministic `src/offers/` calculations, integer minor currency units, explicit timezone and source citations. No silent time/DST, currency, tax, fee, minimum-spend or service assumption. Ask once per unresolved field/version and batch related questions; customer questions become drafts requiring approval. Owner policy questions remain in-app.
- Default authority: explicit approval per consequential outbound action/bundle, no standing send approval. Concessions off. An owner may confirm a scoped concession policy (maximum cumulative reduction, floor, dates/packages/customer scope); proposal validation and pre-dispatch validation both enforce it. Commercial permission to propose a discount does not authorize sending.
- Approval binds booking, proposal version/fingerprint, recipients, exact email/hold action content and policy versions, with expiry. Body, price, date, scope, recipient or terms changes invalidate it; activity-only/UI formatting changes do not. Approvals expire with the offer (reference default: 48 hours or event start, whichever is earlier). No approval is synthesized from an owner-like message.
- Recheck relevant Calendar state immediately before hold mutation (maximum age 60 seconds; configurable stricter value), then recheck cancellation, control state, version and authority after awaits. A 60-second freshness bound does not promise an atomic reservation at Google; conflict on verification blocks confirmation.

## C06 — Durable progression, state and external effects

- One progression owner: extend the existing operator host/drain. `CoordinationLedger` owns waiting/events; existing booking execution claims own provider dispatch; a new intent envelope owns user-visible progress. These are composed, not three schedulers. Disable duplicate independent timers for the same work; one installation process lock plus persistent leases/fencing.
- `Intent`: stable command key, kind, booking/version if relevant, mode, state, step references, lease/fencing, deadline, runId if any, timestamps. States `queued -> running -> completed | retryable | uncertain | blocked | cancelled`. Reclaim expired leases only after checking actual run/effect status. Duplicate key with different payload conflicts. Steps reference existing action/receipt rows, never copy receipts into another truth store.
- Submit validates and commits before `202 {intentId}`; `GET /api/intents/:id` reads persisted progress. Keep existing synchronous service methods for internal callers/tests. Introduce async route behaviour with matching host changes and explicit API documentation; do not break old clients accidentally.
- Planned runner ports: `enqueue(command, expectedVersion)`, `claimDue(now, owner)`, `advance(intent, lease)`, `reconcile(operationKey)`, `cancel(intent, owner)`, `get(intentId)`. Integrate existing `claimDueWork`, `applyOwnerControl`, booking execution claims and provider reconciliation rather than bypassing them.
- External action identity includes mode, business, booking, approved action/version and step. Persist the attempt identity before dispatch. Success before local receipt persistence is **uncertain**, not failure safe to retry. Re-read provider state using stable correlation; a missing record alone is insufficient. Retry only after affirmative no-effect proof or provider-supported idempotency; otherwise block for reconciliation. Never promise exactly-once delivery from a queue alone.
- Holds belong to booking/resource/window, not to every offer price version. Price-only revision reuses the verified same hold and creates only the newly approved email action. Date/resource changes require explicit replacement/release actions with approval; preserve old receipts. Do not silently add a second hold. Expired holds need new authority; no resurrection on replay.
- Booking progress: inquiry/qualification -> proposed -> approved -> provisional -> accepted -> confirmed, with explicit blocked/paused/cancelled control states and per-action receipts. Use existing domain types through adapters; do not force a destructive enum rewrite. Hold success with email failure remains partial. Accepted/confirmed state cannot be downgraded by replay. Cancellation blocks unsent work and offers an approved hold-release action; it cannot undo email already sent.

## C07 — Replies, follow-ups, takeover and acceptance

- Use the existing identity and waiting ledger. Process fresh replies/changes before due follow-ups; if sync is failed/stale, block follow-up sending. Revalidate again immediately before dispatch. Default one follow-up draft after 24 hours without reply; never send it automatically. Further follow-ups need a new owner decision. Reference hold expiry is 48 hours or event start, whichever comes first; release/replacement is a separate approved action unless explicitly included in the original exact bundle.
- Pause/takeover stops new effects but continues evidence ingestion. Resume reconciles new replies, provider effects, hold state and proposal versions first; previous approval cannot become fresh by resuming. Do not equate an inbound customer cancellation request with owner authority to execute cancellation effects.
- **Local-first customer acceptance transport:** use a signed `mailto:` acceptance link in the offer. It opens a reply to the connected business mailbox containing a version-bound opaque token; the customer must send it. Clicking/opening alone never accepts anything. This avoids an unusable remote-customer `localhost` URL and does not require a public acceptance server. Label the link `Accept by email` and explain the send step. Offer copy also supports replying in the same thread; ambiguous plain “yes” requires review.
- Store token binding fields server-side: installation/business, booking, offer version/fingerprint, authorized normalized sender, issued/expiry times, nonce digest and key version. The link carries only a random opaque handle and its signature from a local secret, not the binding payload. Do not put prices, customer details or secrets into URL telemetry/logs. On receipt, require correlation through the token to the persisted original offer-send receipt, exact current offer, unexpired signature, authorized sender and trusted provider authentication evidence; absent/ambiguous authentication becomes review, not auto-acceptance. A signed-token reply may arrive in a new mail thread: its validated token supplies correlation, not a subject/name guess. A plain yes without a token still requires the original unambiguous provider-correlated thread. A forwarded/stolen token from another sender fails. Store token-use digest and acceptance atomically; exact duplicate returns the same record. Reissue supersedes previous tokens; deletion/key rotation invalidates outstanding ones.
- Route replies already correlated to an existing booking and candidate acceptance tokens to their scoped validators before applying the new-inquiry domain gate; an acceptance reply need not repeat an event date or guest count. A token-looking string alone grants no identity or authority.
- Plain “yes” is supported only when exactly one current offer is unambiguously correlated to that authenticated customer/thread. Otherwise request clarification; an LLM's confidence is not acceptance authority.
- Accepted is not confirmed. Reuse `src/delivery/` and `src/server/booking-delivery/`: all configured conditions need authoritative evidence tied to the accepted version. The reference fixture requires acceptance and a fresh uncontested resource commitment; no deposit is required. A live business requiring payment/resources stays provisional until appropriate evidence or an explicitly permitted owner waiver exists. Payment collection remains excluded. Handoff shows event/timezone/services/terms/responsibilities/outstanding conditions and provenance.

## C08 — Runtime, budgets and repair ports

- ADR-009 owns `RuntimeControl`: `provision(pinnedManifest)`, `start`, `health`, `submit`, `observe`, `stop`, `backup`, `restoreCompatible`. These are Gather adapter methods mapped to supported OpenClaw APIs, not invented upstream RPCs. Existing `GatherOpenClawRuntime`, process/client/tasks and MCP boundary are reused. Record one exact tested runtime/client/plugin combination in the manifest; never install `latest`. Candidate compatibility starts from the existing pinned client and documented supported runtime, with capability checks before activation.
- Prepared has a scripted implementation of the same port, never calls provision. Live model login choices are shown only when supported by the pinned runtime/provider and verified; no promise that every subscription works. Secrets are local file-backed refs with owner-only permissions; no inherited developer credentials, channels or personal state.
- Defaults: 15 tool calls, 32,000 total input/output tokens per run, 5-minute execution deadline, 50 runs per business per day. Values are configurable before running. Reserve the next call's maximum input/output budget before dispatch; reject if it cannot fit. Account retries and repair diagnosis against budgets. Persist usage/reservations over restart. A provider with no enforceable bounded output/usage support cannot claim a hard token cap or be enabled for the capped live profile.
- `agent.wait` timeout is observation-only, as existing `src/runtime/tasks.ts` already states. Enforce a real run deadline, fence further Gather tools and request supported cancellation; if needed stop only the owned isolated process and verify exit. In-flight provider effects remain uncertain until reconciled. Never start a duplicate run because a wait expired. Unproved exit stays blocked/unknown.
- Supervisor is outside the booking agent; health checks cannot depend on that broken agent answering. Known faults use deterministic catalog selection. Unknown diagnosis uses a separately budgeted model call with read-only redacted evidence and catalog choices only; invalid/unavailable diagnosis -> blocked. No unrestricted shell tools or automatic runtime upgrades.

## C09 — Repair catalog and proof

| Action | Preconditions | Required verification |
| --- | --- | --- |
| restart_runtime | Owned process identified; no unrelated instance; fence affected runs | Observed old exit, new protocol-ready handshake and useful bounded read; reconcile pending effects before resuming |
| resume_sync_from_cursor | Valid durable checkpoint; authorized account; no concurrent scan lease | Progress beyond checkpoint, stable-key dedupe, coverage state truthful |
| reconcile_execution_by_external_id | Persisted operation identity and authorized provider read | Matching scoped provider result linked to original action; unknown remains blocked |
| refresh_access | Refresh credential exists and consent not revoked | Authorized harmless read works; no token in logs |
| request_reconnect | Revoked/expired access not repairable with existing authority | Visible reconnect action; incident stays blocked until successful consent and read |
| rollback_config_known_good | Validated compatible backup; affected runs fenced | Matching schema/runtime/config restored, useful read, external reconciliation; no business policy/approval rollback |
| rerun_resumable_intent | Predecessor effect known, current authority valid, lease held | Only incomplete steps advance; original completed receipts unchanged |
| mark_blocked | Unsafe/unknown outcome or exhausted bounded attempts | Persisted reason, evidence, attempts and next owner/action; no false recovery |

Three attempts maximum per incident; do not repeat an unchanged action without new evidence. A known permanently denied action may block immediately; use a transient repeatedly failing fixture to test exhaustion. Deduplicate by affected resource/operation plus signature, not signature alone across unrelated bookings. Declare technical restoration separately from useful booking continuation.

For code defects, create an isolated reproduction, proposed patch and regression test under `.runtime/repairs/<incident>/` for operator review. Never apply to the running application. If diagnosis cannot produce a patch, say so and retain a blocked incident; a Markdown suggestion is not a tested patch. No self-modification of commercial authority or future business strategy.

## C10 — UI, evaluation and evidence

- Views: Today, Booking, Connections, Business understanding, Recoveries and evaluation trend. Show only persisted states, cited facts, exact proposed actions, outstanding conditions and actionable errors. Accessible focus/keyboard flow and 1440x900 / 390x844 checks are required; no internal API jargon in owner flows.
- Default notifications are in-app: consequential approval, reconnect, deadline or unrecovered incident. Group routine progress; no unsolicited email/push setup. No OS notification permission requirement for the hackathon.
- Corrections create owner-confirmed regression expectations. Compare before/after on the **same versioned case set**; show score numerator/denominator and case-set version. New cases may change the denominator and must not be presented as improvement on an unchanged set. No guarantee every correction makes a score rise. Semantic evaluation is optional/calibrated, not an authority or provider receipt.
- Source/provider evidence labelled `prepared`, `scripted-runtime`, `real-runtime`, or `live-provider`. Default checks need no external account/model. Real runtime and live effects are separately opted in on controlled accounts. Screenshots alone cannot prove persistent state, remote delivery or recovery.

## C11 — Live connection and external prerequisites

- Direct Google is the selected initial connector implementation. Gather's operator supplies the desktop OAuth client configuration and required Picker project/API settings; customers do not create a Cloud project. Use loopback OAuth with state/PKCE and exact callback ownership, browser-hosted Picker for selected documents and secret-store refs. Required capabilities: `openid email` for account identity, `gmail.readonly gmail.send`, `calendar.events` for event operations, `calendar.freebusy` for the existing freeBusy query, and `drive.file` for selected documents. Adapt existing scope checks to these actual capabilities; do not retain a mandatory `drive.readonly`/`calendar.readonly` check when a narrower granted scope supports the operation. Bind the primary calendar by default; listing other calendars requires a separately disclosed list-read scope rather than silently requesting full Calendar access. Existing direct adapters stay behind their interfaces.
- Do not assume an unverified app can onboard arbitrary judges: testing users, scope restrictions, token expiry and verification requirements must be evidenced with the configured client. Never promise an `Advanced -> continue` bypass. Picker origin/client restrictions are a capability gate, not a reason to silently broaden Drive scopes.
- Composio is a contingency, **not an automatic fallback or second implementation assignment**. If direct onboarding is blocked, preserve its evidence and return the concrete access/configuration issue to Chief. Changing to an operator-hosted broker needs an explicit reviewed amendment including cost, credentials, data flow and deployment authority. Prepared mode remains usable; live cannot be declared complete.
- Capability gates belong to the relevant implementation ADR and have fixed success/failure outcomes; they are not missing product decisions for Orca to invent. Lack of authorized accounts, keys, credits or registrations blocks the corresponding live proof, not local implementation/testing. No purchase/deployment/registration authority is implied by the plan.

## C12 — Sponsor profiles and release

- One engine, explicit profiles: base, AssemblyAI voice, Amazon owner interface, Nebius/NVIDIA model. Disabled adapters perform no network activity and receive no data. Package integration uses a shared profile registry, with credentials provided outside Git. Never silently fall back from a required sponsor provider to another.
- Voice translates an actual authorized recording into C02 intake; uncertain transcription requires clarification before commercial actions. Amazon adds an authenticated owner-facing MCP surface, not customer-supplied approval authority. Nebius routes an actual booking reasoning call through a qualifying verified NVIDIA model/provider configuration. Each event needs independent receipts and reused/new-work provenance.
- The operator-facing Amazon MCP demonstration is loopback/self-hosted unless a separately authorized secure external deployment is supplied. A simulated Alexa-facing client is labelled; do not claim Alexa platform acceptance from a local MCP smoke test. Verify the selected submission route against current official rules.
- Release gate maps every PRD section-10 row plus section-11 event requirement to evidence; no ADR completion alone establishes release completion. A requested event can be evaluated independently; an all-events release requires all three adapters. Keep no fabricated demo link: record video only after the actual flow works, and do not publish/submit automatically.
